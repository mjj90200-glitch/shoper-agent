# 9.16 开发记录：P0 收尾（asyncmy 可复现性修复 + 安全门禁清零）

## 开发目标

完成 P0 遗留的补充验收：修复全新克隆环境 `uv sync` 失败的问题，清零安全扫描高危发现，使「全新克隆按 README 安装」的验收标准可以真实通过。

## 根因分析

- 现象：`uv sync --frozen` / `uv run` 在 Python 3.14 环境构建 `asyncmy 0.2.11` 时源码编译失败。
- 根因：`uv.lock` 锁定的 asyncmy 0.2.11 只有 sdist、没有任何 cp314 Windows 轮子（cp314 win_amd64 轮子自 0.2.12 起才提供），无本地 C++ 编译环境时必然失败。
- 佐证：工作 `.venv` 中早已安装的 asyncmy 0.2.14（有 cp314 轮子）一直正常工作；PyPI 元数据显示 0.2.12/0.2.13/0.2.14 均提供 cp314 win_amd64 轮子。

## 本次完成内容

### 1. 升级锁文件中的 asyncmy（`f8f86b2`）

- `uv lock --upgrade-package asyncmy` 将锁定版本 0.2.11 → 0.2.14。
- 满足 `pyproject.toml` 的 `asyncmy>=0.2.11` 约束，零代码改动，其余 121 个包锁定不变。

### 2. 修复评测脚本 SSRF 高危（`0ae2877`）

- 安全门禁在提交时拦截出 `evaluate_query_api.py` 两处 `urlopen(变量 URL)` SSRF 高危（原有 `noqa: S310` 豁免不被认可）。
- HTTP 层从 `urllib.request` 迁移到项目已有依赖 `httpx`，并对非 2xx 响应补 `raise_for_status()` 保持原有失败语义。
- 新增 `validate_base_url`：仅允许 http/https、拒绝携带用户名密码、必须有主机名。
- 新增 4 个校验单元测试；对运行中的本地后端真实登录冒烟通过。

### 3. 清除 qdrant 调试脚本低危告警（`91ea0ec`）

- `__main__` 调试向量从 `random.random()` 改为 `random.SystemRandom().random()`，清除 CWE-330 不安全随机数低危发现。

## 关键决策

- 不降级 `requires-python >= 3.14`、不更换 MySQL 驱动：升级锁定的 asyncmy 版本是满足约束的最小修复。
- 修复提交按「一次提交一个工程变化」拆分为三笔：锁文件、SSRF、随机数各自独立。
- `v0.2.0` 标签与 Release 维持计划要求，等待远程 CI 验证通过后单独确认。

## 验证结果

- 一次性临时 venv `uv sync --frozen`：120 包全部安装成功，asyncmy 0.2.14 走轮子，核心模块导入正常。
- 全新克隆（新 HEAD `91ea0ec`）`uv sync --frozen`：成功；`pnpm install --frozen-lockfile`：成功（12.4s）。
- 统一质量门禁 `uv run python -m app.scripts.quality_check`：Ruff 通过、后端测试 57/57、前端 tsc + 生产构建通过。
- 加入新测试后全量后端测试：61/61 通过。
- Mimosa 复扫（聚焦改动文件）：高危 0、中危 0；低危 2 处已在 `91ea0ec` 清除。
- 评测脚本 `login()` 对运行中后端冒烟：真实拿到 access_token。

# 9.16 开发记录（续）：P1-A 配置校验与启动诊断

## 开发目标

按工程优化计划进入 P1 阶段第一项：把 import 时的全局配置加载收敛为可注入、可校验、启动快速失败的单一 Settings 入口。

## 根因与现状确认

- `app_config.py` 在模块 import 时完成 `.env` 读取与 `${oc.env:...}` 插值，任何必需变量缺失都会让 import 崩溃。
- CI 靠 workflow 硬编码 `LLM_API_KEY: test-only-key` 等环境变量才能通过测试，属于临时补丁。

## 本次完成内容

### 1. 单一配置入口（`53249cb`）

- 新增 `app/conf/settings.py`：`load_app_config` 纯函数（可注入 environ/yaml_text/load_env_file）、`ENV_FIELDS` 显式环境变量覆盖表、`ensure_runtime_ready` 启动校验、`get_app_config`/`reset_app_config_cache` 缓存。
- `conf/app_config.yaml` 移除全部 `${oc.env:...}` 插值，改为静态默认值；`AppConfig` 新增 `app_env` 字段（`APP_ENV`，默认 dev）。

### 2. 迁移全部导入者（`0814b99`）

- 9 个模块从 `from app.conf.app_config import app_config` 迁移到 `get_app_config()`；删除 `app_config.py` 的模块级加载，仅保留类型定义。
- 实测：隐藏 `.env` 并清空密钥环境变量后 `import app.api.lifespan` 成功。

### 3. 启动快速失败（`8839b28`）

- `lifespan()` 首步调用 `ensure_runtime_ready(get_app_config())`；缺失必需变量时启动即退出，错误只列变量名。
- 删除 `ci.yml` backend job 硬编码的测试环境变量。

## 关键决策

- 环境变量映射从 YAML 插值改为代码中的显式覆盖表：可枚举、可单测，空串视为未设置，TTS 密钥为空时映射为 None 保持功能可用。
- 两阶段校验：加载只做结构校验（不要求密钥），启动校验才要求必需变量非空——同时满足「缺失即快速失败」与「测试不依赖 .env」两条验收。
- `meta_config.py` 与 `conf/auth_config.yaml` 保持现状：前者无环境变量，后者属于 P2-D 的认证治理范围。

## 提交清单

- `53249cb` settings 统一配置入口
- `0814b99` 导入者迁移
- `8839b28` 启动快速失败 + CI 环境变量移除
