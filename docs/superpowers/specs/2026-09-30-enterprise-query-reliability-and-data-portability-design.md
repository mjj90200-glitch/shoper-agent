# 企业级查询可靠性与数据可迁移能力设计

- 日期：2026-09-30
- 项目：`shopkeeper-agent` Web/后端与 Android 客户端
- 方案：B（渐进式企业化增强）
- 状态：设计已确认，待实施计划
- 代码仓库：后端/Web 使用 `mjj90200-glitch/shoper-agent`；Android 使用 `mjj90200-glitch/shoper-agent-android`

## 1. 背景

当前项目已经具备多轮问数、元数据召回、只读 SQL 防护、数据库执行、确定性结果分析、查询审计和历史会话等基础能力，但还不能把现有测试成绩等同于企业级可靠性。

已确认的当前状态如下：

- `app/agent/nodes/rewrite_query.py` 只向改写模型提供最近 10 条成功消息，约 5 轮问答；更早消息由 LangGraph SQLite checkpointer 保存，但没有真正的上下文摘要或压缩。
- 当前评测报告的单轮结果良好，但评测场景最长只有 2 轮，不能证明连续 5 至 20 轮追问不会混乱。
- SQL 在执行前经过只读 AST、数据库范围、危险关键字和 `EXPLAIN` 等检查；数据库结果及结果洞察来自真实查询，不由模型虚构。
- 语法合法并不代表业务语义正确。元数据召回遗漏、指标理解错误、错误连接路径或过期索引，仍可能产生“SQL 可执行但答案不正确”的情况。
- MySQL 元数据当前以 `add_all` 写入，Qdrant 使用随机 UUID，Elasticsearch 虽使用确定性文档 ID，但完整重建不会自动清除所有已移除值。因此重复构建可能出现主键冲突、向量重复或旧索引残留。
- 当前业务表之间没有数据库声明的外键约束，连接关系主要通过字段角色、字段名和提示词推断，缺少可验证的显式关系目录。

本设计在不推翻现有 LangGraph、FastAPI、MySQL、Qdrant 和 Elasticsearch 架构的前提下，补齐多轮可靠性、语义校验、数据版本化和端到端验证能力。

## 2. 目标

### 2.1 产品目标

1. 经过验证地支持至少 20 轮连续业务对话，其中至少 10 次追问依赖前文。
2. 在生成 SQL 前判断问题是否可回答，不存在的指标、字段和值不得被猜测执行。
3. 数值、排名、占比、合计和图表数据必须能够追溯到真实 SQL 结果。
4. 数据库结构、指标、字段说明和业务数据更换后，可以安全重建元数据与向量索引。
5. 新数据版本必须先隔离构建和验证，再原子切换；失败时不影响当前版本，并可回滚。
6. Web 与 Android 使用同一份结构化查询协议和错误状态。

### 2.2 工程目标

1. 每项改动使用独立分支和独立 GitHub PR。
2. 每个 PR 都包含测试证据、数据影响、风险和回滚办法。
3. 不直接向 `main` 提交功能代码，不在用户审查前合并 PR。
4. 通过单元、集成、确定性端到端和真实模型评测形成分层质量门槛。

## 3. 非目标

第一阶段明确不做以下工作：

- 不重写整个 Agent 或替换 LangGraph。
- 不把所有存储迁移到新的基础设施。
- 不同时支持 PostgreSQL、Oracle、SQL Server 等多种数据库；先稳定支持可配置的 MySQL 数据集。
- 不建设复杂的数据管理后台；第一阶段以受控命令行工具、健康检查接口和构建报告为主。
- 不保证无限轮对话；首个明确质量目标是 20 轮，架构应保持上下文大小有界并允许继续扩展。
- 不让 Android 客户端复制 SQL 生成、语义校验或指标计算逻辑。

## 4. 方案选择

采用方案 B：渐进式企业化增强。

方案 A 只增加历史窗口和提示词，改动较小，但不能解决语义错误、索引重复和数据回滚问题。方案 C 将元数据、任务队列和会话设施全面服务化，长期扩展性更强，但对当前自用阶段成本过高。

方案 B 保留现有技术栈，通过明确边界逐步增加六类能力：质量基线、结构化记忆、语义目录、版本化发布、QueryPlan 校验和数据集运维工具。各阶段可以独立测试、审查和回滚。

## 5. 总体架构

查询链路调整为：

```text
用户问题
  ↓
会话隔离与结构化记忆
  ↓
问题改写
  ↓
元数据/字段值召回
  ↓
结构化 QueryPlan
  ↓
可回答性、指标、字段、值与连接路径校验
  ↓
SQL 生成与只读安全校验
  ↓
固定数据版本上的数据库执行
  ↓
确定性结果分析与结构化 API 事件
  ↓
Web / Android 展示
```

数据维护链路调整为：

```text
扫描新数据源
  ↓
生成新旧差异报告
  ↓
在隔离版本中构建 MySQL 元数据、Qdrant 集合和 ES 索引
  ↓
完整性与回归验证
  ↓
人工确认激活
  ↓
原子切换活动版本指针
  ↓
保留旧版本用于回滚
```

每次请求在开始时解析并固定一个数据版本，直到请求结束都不得跨版本读取。

## 6. 多轮对话与结构化记忆

### 6.1 两层工作记忆

模型的工作上下文由两部分组成：

1. 最近原文：保留最近 5 轮成功的数据查询及其结果摘要。
2. 结构化摘要：承载更早对话中仍然有效的业务语义。

结构化摘要至少包含：

- 当前指标及指标 ID；
- 分组维度；
- 筛选条件和已解析实体；
- 时间范围与时间粒度；
- 排序和数量限制；
- 对比对象；
- 上一条已验证 QueryPlan 的语义摘要；
- 尚未解决的指代或歧义。

达到消息数量或估算 Token 阈值时更新摘要，并裁剪进入模型提示词的旧原文。完整查询历史继续保存在现有审计数据中，不依赖模型工作记忆承担审计职责。

只有成功完成并可用于后续指代的数据查询可以更新业务记忆。闲聊、能力说明、失败查询和系统错误可以保留在审计历史中，但不得成为后续查询条件。

### 6.2 隔离范围

会话键从逻辑上定义为：

```text
tenant_id + username + session_id
```

个人版本使用默认租户，仍保留租户字段和边界。相同用户的不同会话、不同用户以及未来不同租户之间必须完全隔离。Android 与 Web 只有在使用相同账号和相同会话 ID 时才共享上下文。

### 6.3 压缩行为

- 摘要是结构化字段，不使用无法校验的自由文本作为唯一记忆。
- 摘要更新失败时保留上一份有效摘要，并以本轮原始问题继续处理；失败必须记录审计事件。
- 新建会话不得继承旧会话摘要。
- 服务重启后应从持久化 checkpointer 恢复最近消息和摘要。
- 上下文输入必须有明确的消息和 Token 上限，不能随会话轮数无限增长。

## 7. QueryPlan 与查询正确性

### 7.1 QueryPlan

自然语言不能直接进入 SQL 生成节点。系统先生成具有明确 Schema 的 QueryPlan，至少包含：

```text
metrics
dimensions
filters
time_range
time_grain
order_by
limit
join_path
evidence
answerability_status
```

`evidence` 记录每个指标、字段、值和连接路径来自哪个已激活的元数据版本。QueryPlan 校验通过后才能生成 SQL。

### 7.2 可回答状态

统一状态定义为：

- `answerable`：信息充分且全部语义要素得到验证；
- `needs_clarification`：有多个可能含义，需要用户确认；
- `unsupported_metric`：指标不存在或没有经过配置；
- `unknown_field`：字段不存在或当前用户不可使用；
- `unknown_value`：筛选值不能在活动数据版本中确认；
- `invalid_join`：没有允许的连接路径；
- `no_data`：查询合法，但数据库没有匹配记录；
- `execution_error`：依赖服务或 SQL 执行失败。

除 `answerable` 外，其余前置状态不得进入 SQL 执行。`no_data` 只会在合法 SQL 执行完成且返回空结果后产生。

### 7.3 防止错误结论

- 指标公式只能来自活动指标目录，不允许根据常见业务知识临时创造。
- SQL 只能使用 QueryPlan 已确认的表、字段和连接路径。
- 数值、排名、合计、平均值和比例由程序根据数据库结果计算。
- 自然语言层只能组织已经验证的事实，不得新增结果中不存在的数值。
- QueryPlan、生成 SQL、数据版本、执行结果摘要和最终回答通过同一追踪 ID 关联。

## 8. 语义目录与显式表关系

在现有 `table_info`、`column_info`、`metric_info` 和 `column_metric` 基础上，引入版本化的数据集和关系定义。关系目录的逻辑字段至少包括：

```text
relationship_id
dataset_version
source_table
source_column
target_table
target_column
relationship_type
join_type
enabled
```

数据库已声明的真实外键可以被扫描导入；未声明外键时，必须在数据集配置中显式声明。系统不再仅通过同名字段或提示词猜测 JOIN。

关系校验至少检查：

- 表和字段真实存在；
- 数据类型兼容；
- 连接方向与基数有效；
- 不存在未授权的跨数据集连接；
- 不存在会导致无界组合的错误连接路径；
- 指标引用的字段和维度都属于同一个可达关系图。

## 9. 数据版本化、构建与回滚

### 9.1 数据发布包

一次发布由统一的 `dataset_release` 表示，绑定以下内容：

- 业务数据源或可恢复的数据快照；
- MySQL 元数据和关系目录版本；
- 指标定义版本；
- Qdrant 字段集合和指标集合；
- Elasticsearch 字段值索引；
- 构建配置摘要、差异报告和验证报告。

发布状态为：

```text
BUILDING → VALIDATING → READY → ACTIVE
     │          │
     └──────────┴──→ FAILED

ACTIVE → RETIRED
RETIRED → ACTIVE
```

未达到 `READY` 的版本不得激活。任何时刻一个数据集只有一个活动发布版本。

### 9.2 幂等构建

- MySQL 元数据使用版本键和 upsert，不再依赖盲目 `add_all`。
- Qdrant 点 ID 由数据集、版本、对象类型和稳定业务键确定性生成。
- Elasticsearch 文档 ID 使用相同的稳定标识策略。
- 每个新版本使用隔离集合或索引，已删除字段和值不会从旧版本泄漏到新版本。
- 相同输入重复构建相同版本，最终内容和数量必须一致。

### 9.3 蓝绿切换

新版本在独立资源中完成构建和验证。激活时只更新一个统一的活动发布指针；Qdrant 和 Elasticsearch 可以通过别名或等效的版本解析机制完成切换。所有子资源都准备完成后才允许更新指针。

切换前已经开始的请求继续使用旧版本；切换后开始的新请求使用新版本。旧版本不会立即删除，可以通过重新激活完成回滚。

### 9.4 回滚边界

完整回滚需要保留对应的业务数据源或快照。若直接覆盖业务表且没有备份，只能回滚元数据和索引，无法恢复被覆盖的业务数据。正式更换数据集时，应使用新数据库、新 Schema、独立实例或可恢复快照。

删除旧版本是单独的显式运维动作，默认不随激活自动发生。

## 10. 数据集更换流程

第一阶段支持在 MySQL 范围内：

- 更新现有表的数据；
- 增加、删除或改名表和字段；
- 修改字段说明、指标定义和连接关系；
- 切换到另一套 MySQL 数据库或 Schema；
- 保存多套互相隔离的数据源配置。

正式构建前生成差异报告。新增字段通常是兼容变更；删除字段、修改数据类型、删除指标、改变连接路径或向量维度属于破坏性变更，默认阻止自动激活，必须由操作者显式确认并通过完整回归测试。

数据源密码、API 密钥等敏感信息只通过环境变量或密钥机制注入，不写入 Git、YAML、日志或构建报告。

## 11. API 与客户端契约

后端继续通过 SSE 提供查询进度，但增加稳定的结构化事件或等效响应字段，至少包含：

- `trace_id` / `audit_id`；
- `query_status`；
- `dataset_version`；
- 澄清问题或不可回答原因；
- 结果列、结果数据和确定性洞察；
- 可安全展示的错误代码。

Web 和 Android 不根据错误文本猜状态，而是消费结构化状态码。Android 只负责登录、会话管理、流式状态和结果展示，不包含数据库连接、SQL 生成或指标计算逻辑。

后端协议完成后，Android 单独适配以下状态：需要确认、不支持的指标、未知字段/值、合法但无数据、网络失败和服务器执行失败。

## 12. 错误处理与可观测性

每次查询记录：

- 租户、用户、会话和追踪标识；
- 使用的数据版本；
- 结构化 QueryPlan 及校验状态；
- 生成 SQL 和执行结果行数；
- 各节点耗时；
- 错误代码，不记录敏感凭据；
- 最终状态和用户反馈。

每次数据发布记录：

- 构建者、开始/结束时间和发布状态；
- 数据源结构摘要和新旧差异；
- MySQL、Qdrant、Elasticsearch 对象数量；
- 完整性检查和回归结果；
- 激活、回滚及旧版本清理操作。

依赖服务失败、版本不一致或校验失败时采取失败关闭策略：保持当前活动版本，不进行部分激活。

## 13. 测试与验收策略

### 13.1 测试分层

1. 单元测试：摘要压缩、QueryPlan Schema、可回答性规则、关系校验、确定性 ID 和状态转换。
2. 集成测试：连接真实 MySQL、Qdrant 和 Elasticsearch，验证构建、切换和查询。
3. 确定性端到端测试：固定模型响应，作为 PR 的强制 CI 门槛。
4. 真实模型评测：使用实际模型运行问题集，报告成功率和全部失败样本。
5. Web 端到端测试：登录、提问、连续追问、历史会话、图表和错误状态。
6. Android 端到端测试：模拟器完成登录、连续追问、断网恢复和数据版本切换验证。
7. 回滚演练：激活新版本后切回旧版本，并校验关键查询的精确结果。

### 13.2 核心验收标准

- 连续 20 轮业务对话，至少 10 次依赖前文的追问正确。
- 不同租户、用户和会话之间零上下文串扰。
- 服务重启后会话状态正确恢复。
- 发送给模型的上下文保持在固定预算内。
- 不存在的指标、字段和值不会进入 SQL 执行。
- 含义不明确的问题返回澄清状态。
- 关键查询使用固定种子数据校验精确数值，而非只检查 SQL 文本。
- Web 与 Android 对同一查询得到一致的结构化业务结果。
- 同一数据版本连续构建三次不产生重复记录。
- 构建失败不影响活动版本。
- 删除字段和值后，新版本没有旧索引残留。
- 切换时正在执行的查询保持版本一致。
- 回滚后关键查询恢复为旧版本的精确结果。

## 14. PR 拆分与交付顺序

### PR 1：企业级质量基线

- 分支：`feat/enterprise-quality-baseline`
- 增加固定种子数据、精确结果断言、20 轮场景、隔离场景和 GitHub Actions。
- 不改变生产查询逻辑；当前未达到的目标记录为基线缺口，不能伪装成通过，也不能让主分支长期失败。

### PR 2：结构化对话记忆

- 分支：`feat/structured-conversation-memory`
- 实现最近原文加结构化摘要、压缩阈值、持久化恢复和三级隔离。

### PR 3：语义目录与显式关系

- 分支：`feat/semantic-catalog-relationships`
- 增加版本化数据集、关系目录、关系扫描和配置校验，并补全当前业务表关系。
- 数据库迁移必须同时提供升级和回滚路径。

### PR 4：版本化元数据发布

- 分支：`feat/versioned-metadata-releases`
- 实现幂等写入、确定性 ID、隔离构建、验证、原子激活和回滚。
- 若审查体积过大，拆分为“幂等构建”和“蓝绿切换”两个连续 PR。

### PR 5：QueryPlan 与可回答性校验

- 分支：`feat/query-plan-validation`
- 实现 QueryPlan、指标/字段/值/连接校验、标准状态和确定性结果约束。

### PR 6：数据集发布工具

- 分支：`feat/dataset-release-tooling`
- 提供扫描、差异预览、构建、验证、激活、回滚、健康检查和运维文档。

### Android 适配 PR

- 仓库：`mjj90200-glitch/shoper-agent-android`
- 分支：`feat/enterprise-query-states`
- 在后端协议稳定后适配结构化状态、澄清交互、数据版本和追踪 ID，并完成模拟器验证。

依赖 PR 按顺序实施。前一个 PR 推送并交由用户审查后，才进入依赖它的后续 PR；任何 PR 未经用户批准都不合并。

## 15. 每个 PR 的强制交付内容

每个 PR 都必须包含：

- 问题与目标；
- 实际修改和明确未修改的范围；
- 数据库、API 和客户端兼容性影响；
- 风险与回滚步骤；
- 单元、集成和端到端测试结果；
- 真实模型评测结果或不适用说明；
- 需要用户重点检查的文件、截图或日志。

开发过程遵循：独立分支、先写失败测试、实现最小改动、完成分层验证、推送 GitHub、创建 PR、等待用户审查。不得将多个无关重构混入这些 PR。

## 16. 风险与缓解

| 风险 | 缓解措施 |
| --- | --- |
| 结构化摘要丢失重要条件 | 保留最近原文；摘要采用 Schema 校验；加入 20 轮回归用例 |
| 真实模型输出具有波动 | CI 使用确定性模型替身；真实模型评测单独报告失败样本 |
| 表关系配置错误造成语义错误 | 激活前验证字段、类型、基数和固定查询结果 |
| 多存储切换出现部分成功 | 先构建全部子资源，最后只切换统一活动版本指针 |
| 新数据版本无法恢复 | 激活前要求保留旧数据源或快照；旧版本默认不自动删除 |
| PR 体积过大难以审查 | 按能力拆分；PR 4 必要时继续拆成两个连续 PR |
| API 改动破坏 Android | 后端先提供稳定结构化协议，Android 在独立仓库后续适配 |

## 17. 完成定义

只有在以下条件同时满足时，本次企业化改造才视为完成：

1. 六个后端/Web PR 和必要的 Android 适配 PR 均经过用户审查并合并；
2. 核心验收标准全部通过，测试证据保存在 CI 或评测报告中；
3. 数据版本切换与回滚在本地 Docker 环境完成一次真实演练；
4. Web 与 Android 模拟器完成同一套关键业务流程；
5. 数据更换、故障诊断、回滚和旧版本清理均有可执行文档；
6. 当前生产数据和现有用户流程没有未经批准的破坏性变化。
