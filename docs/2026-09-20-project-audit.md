## 确认的问题及修复顺序

### P1：用户隔离与查询边界

1. **本地工作区缓存未按账号隔离。** `frontend/src/lib/workspaceStorage.ts` 使用固定存储键；`useConversations`、`useAnalysisProjects` 切换账号时保留上一账号状态。浏览器已复现从管理员切到区域经理后，仍显示华南/华北/西南等全国结果。分析 Hook 还会把本地项目自动同步到当前登录账号。只读核查 SQLite 时，admin 和 east_manager 各有 3 条项目记录；未建立切换前快照，不能判断这 3 条是否全部由本次操作创建，不应据此删除记录。

   修复设计：缓存按稳定用户标识分区；登录变化时重新装载对应工作区并取消旧请求；完成当前账号加载后才允许自动同步。旧的无归属缓存保留备份，不自动归属给任意登录账号。回归需要覆盖页面显示及发出的保存请求。

2. **区域权限只做文本匹配，不能证明筛选实际约束订单。** 对 east_manager 执行离线检查，以下 SQL 被当前护栏接受：

   ```sql
   SELECT SUM(f.order_amount)
   FROM fact_order f
   WHERE EXISTS (
     SELECT 1 FROM dim_region r WHERE r.region_name = '华东'
   )
   ```

   子查询与订单无关联，只要存在华东记录，外层仍汇总全部订单。探针只调用校验函数，没有执行此 SQL。修复应采用结构化 SQL 校验或受权限约束的数据访问边界；无法证明安全的结构拒绝执行，不能继续叠加简单正则冒充权限保证。

3. **显式 LIMIT 不受结果上限约束。** `guard_sql('SELECT * FROM fact_order LIMIT 99999999')` 原样返回。数据扩容后可能导致大量结果读入内存。需要覆盖 LIMIT、OFFSET、子查询及 CTE 的外层上限，并防止别名/标识符被误判为限制子句。

### P1：分析正确性

4. **图表卡片只统计前 20 行。** 25 行数值 1～25 时，正确合计 325、均值 13、最高 C25；当前卡片得到 210、10.5、C20，但条数显示 25。全量统计必须与图表截断分开。

5. **前后端重复推断标签，摘要和图表口径不一致。** 数字月份加文本备注时，后端选择月份，前端选择备注；页面历史项目亦出现摘要“最高为 1”，卡片“最高项 华东”。后端图表最多 12 点，前端最多 20 点。应统一标签来源和截断契约，维度字段不作为普通指标选择。

6. **地区聚合粒度仍未约束。** 历史 SQL 按省份粒度 `region_id` 分组，却只展示大区 `region_name`；上海、浙江因此都显示“华东”。已有历史页面仍能复现。应在元数据及 SQL 生成/纠错环节明确省份与大区层级，新增业务结果断言。不能删除合法维度记录，也不能直接相加比例。历史报告需重跑后才会有正确的新结果。

### P2：异常处理、配置和验收可靠性

7. **HTTPException 携带响应头时退化为 500。** `errors.py` 对普通字典 `exc.headers` 访问 `.raw`；离线 HTTP 请求稳定复现 401 变 500，认证响应头丢失。应通过 `JSONResponse(headers=...)` 传递。

8. **未处理异常缺少 X-Request-ID，且日志记录自身失败。** 500 由外层异常中间件生成，未经过加响应头的正常返回路径；错误模块直接导入原始 Loguru，绕开 request_id 注入。需保证 500 错误信封、响应头和日志使用同一个追踪编号，增加日志记录的真实断言。

9. **MySQL 密码特殊字符会破坏连接地址。** 使用虚构密码 `test@value` 构造连接后，SQLAlchemy 解析出的 host 已不再是 localhost。应使用结构化 URL 构造器，而非字符串拼接。

10. **现有评测可能假通过。** `evaluate_turn` 对先出现 result、再出现 error 的事件序列返回 `(True, [])`。现有用例主要断言 SQL 片段和事件存在；脚本失败用例也没有非零退出码。需要验证唯一终态、结果行数/数值、分组键唯一性及失败退出码，并保留逐条错误。

11. **运行文档存在误导。** `start.md` 把华东重复写为主数据问题；实际上省份维度拥有相同大区名称合法，错误发生在查询分组与展示层级不一致。启动示例也应与必需 MySQL 环境变量及 Compose 环境文件路径保持一致。
